- **Name, role, value (4.1.2):** all 26 states have no unnamed control. The lists are a real `tablist` / `tab` / `tabpanel` with `aria-selected` and a roving tabindex, and the panel is named by its tab. Both settings confirms are `role=alertdialog` `aria-modal="true"`, named by their `h2` and described by their body. The page behind is `inert`. Focus goes in on open (the add-name field, the sheet's title, and "ביטול" in both confirms, the safe default for a destructive action). Tab wraps inside (add-name: field → "הוספה לרשימה" → "סגירה" → field; confirms: "מחיקה לצמיתות" ⇄ "ביטול"). Escape closes, and focus goes back to the opener ("הוספת שם שלא ברשימה", "מחיקת החשבון", "יציאה מהבחירה המשותפת", the row's name button).
- **Keyboard (2.1.1, 2.1.2, 2.4.3, 2.4.7, 2.4.11):** the Tab order follows the visual RTL order on every screen (back, invite, add, the banner, the selected tab, each row's name then its menu, the duel link; settings top to bottom; hidden's restore buttons). ## Findings

### A11Y-G3-01: The add-name and settings name fields have no visible edge

- **Screen and state:** add-name sheet (default, empty field), `/names/settings` "השם שלי" (solo and shared)
- **Browser:** webkit-iphone · chromium-pixel · sim-safari (the same in all)
- **What's wrong:** add-name's field is `bg-surface` with a `border-line` edge on the white sheet: the edge is 1.34:1 against the sheet and the fill 1.0:1. Until focus draws the ring there's only a hairline to show where to type (`add-name-default-chromium.png`). The settings field is `bg-sand` with `border-line` inside a white card. The fill is 1.18:1 against the card and the edge 1.34:1 outside and 1.13:1 inside, so it reads as a faint beige band next to "שמירה" (`settings-shared-sim.png`). Both are the same problem as A11Y-G1-01 (sign-in, onboarding) and A11Y-G2-02 (report, survey). The add-name error state passes: its `aria-invalid:border-urgent` edge is 6.9:1.
- **Rule it breaks:** `accessibility-audit` · `references/wcag-checklist.md` §3 Non-Text Contrast (1.4.11 AA) · "UI components (buttons, inputs, dropdowns): ≥ 3:1 against adjacent colors"; `accessibility-review` · `SKILL.md` · "1.4.11 Non-text contrast >= 3:1 (UI components, graphics)"
- **Severity:** P2
- **Effort:** XS (once A11Y-G1-01's shared field class exists)
- **Proposed change:** merge with A11Y-G1-01 / A11Y-G2-02. Use the shared text-field class (`border-stone`, 5.7:1 on white) for `#add-name` in `lists/AddNameSheet.tsx:71` (keep `aria-invalid:border-urgent`) and for `#settings-name` in `SettingsScreen.tsx:273`. The settings field moves from `bg-sand` to the same white fill with the stone edge, which also settles IMP-C-G3-16 (the field doesn't follow the input spec). IMP-A-G3-05 (16 px) touches the same two fields, so do them in one pass. Re-measure with `a11y-g1-contrast.py` (edge ≥ 3:1 against the surface in Chromium and Safari).
- **Guardrail:** polish (existing token; same layout)
- **Screenshot:** `audit/A11Y-G3/add-name-default-chromium.png`, `audit/A11Y-G3/settings-shared-sim.png`, `audit/A11Y-G3/settings-solo-webkit.png`

### A11Y-G3-02: Adding a name, saving the display name and leaving a shared choice are announced twice

- **Screen and state:** `/names/lists` after "הוספה לרשימה" with a new name; `/names/settings` after "שמירה" of a changed name and after leaving the shared choice
- **Browser:** webkit-iphone · chromium-pixel (both show the same two regions filled)
- **What's wrong:** each of these actions writes its message to the screen's own sr-only `role=status` (`setStatus`) and also shows it as a toast, whose region is a second `role=status aria-live=polite`. After adding "שמשוני" both regions hold "השם שמשוני נוסף לרשימה" (`listsFlow` "add a custom name", both engines), so a screen reader says it twice. The same pairs are in `SettingsScreen.tsx` (`NAME_SAVED_TEXT` at 141–142, `LEAVE_DONE` at 212–213). This is the same pattern as A11Y-G1-07 ("הקישור הועתק"). The vote from the name sheet in `ListsScreen` also writes both, but there the page is `inert` behind the sheet, so only the toast is heard. That one is right.
- **Rule it breaks:** `accessibility-audit` · `SKILL.md` Layer 3 · "Are status messages announced (success, error, loading)?" (once, clearly); `references/common-issues-and-fixes.md` §12 Missing Status Messages (one live region per message); best practice, not a WCAG failure
- **Severity:** P3
- **Effort:** XS
- **Proposed change:** merge with A11Y-G1-07 and use one rule for all: when a message is shown as a toast, don't also write it to the local status. In `ListsScreen.tsx` `add()` drop `setStatus(addedText(name))`. In `SettingsScreen.tsx` drop `setStatus(NAME_SAVED_TEXT)` and `setStatus(LEAVE_DONE)`. Keep the local status where there's no toast (the opt-in, row remove/hide, restore) and in `decideInSheet` (there the page is inert, so the local status is silent anyway, and the toast is the one heard). Check in both engines that each message sits in one region.
- **Guardrail:** polish (no copy change)
- **Screenshot:** `audit/A11Y-G3/probe-chromium.json` (`listsFlow`, step "add a custom name"), `audit/A11Y-G3/lists-saved-default-chromium.png`

### A11Y-G3-03: Going offline on "התאמות" changes the screen silently

- **Browser:** webkit-iphone · chromium-pixel

The line is a plain `<p>` that appears on its own, and no live region changes (`matchesOfflineLive` is empty in both engines). A sighted person sees the list is from earlier. - **Effort:** XS
- **Proposed change:** in `ListsScreen.tsx` `MatchesPanel` (`updated`, line 313), render the line inside an always-mounted `<p role="status">` (empty while online, the updated text while offline), with the same classes, so its appearance is announced once. Whatever wording IMP-C-G3-18 settles on for this line goes into the same element. Verify with the probe's offline step that the region holds the text.
- **Guardrail:** polish (no layout change; copy per IMP-C-G3-18)
